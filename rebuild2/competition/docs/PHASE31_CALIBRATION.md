# Phase 3.1 校正・診断（競技用の回り込みは無効）

## 先に確認すること

この診断版は**機体を確実に固定し、4輪を床から完全に浮かせた状態専用**。床上では使わない。外部の動力遮断手段を手元に置き、遮断担当者を置く。白線危険、USB切断、カメラ／IRの異常、`s`、150msのソフトウェア期限で診断パルスを中止するが（処理・通信遅延が加わる）、USBや無線の指令だけを非常停止手段にしない。カメラとIRの正常通信が必要で、ボール検知は不要。配線変更は電源を切ってから行う。実機校正、書き込み、駆動は本作業では行っていない。

通常版の `RCJ_PHASE3_ORBIT=0` を維持する。実機で回り込みは動かないため、その動作中の実測ログもまだ存在しない。シミュレーション用には `ORBIT_ACTIVE`、`ORBIT_ELAPSED_MS`、`ORBIT_DIRECTION`、`ORBIT_COOLDOWN` を追加したが、実機用に有効化しようとするとコンパイルエラーになる。現在の実機診断で測れるのは単発の車輪パターンとセンサー情報であり、回り込み完了の検証ではない。

## 配線とPWMの監査

PWM配列順は資料上の位置と `motor.ino` の出力配線の組み合わせ。位置は機体で再確認する。MOTORの正値は表の前側GPIOにPWM・後側を0、負値は前側0・後側GPIOに絶対値PWMを出す。PWM20kHz、範囲0–255、プロトコル最大絶対値210、配列各値は符号付きで送信しMOTORが復元する。回転方向の時計回り／反時計回りは軸をどちらから見たかも記録し、GPIO符号だけで決めない。

| 配列 | 物理名・資料上の位置 | MOTOR正/負 GPIO | 単輪選択 |
|---|---|---|---|
| 0 | M3 左後 | 6 / 7 | `1` |
| 1 | M2 左前 | 12 / 13 | `2` |
| 2 | M1 右前 | 11 / 10 | `3` |
| 3 | M4 右後 | 9 / 8 | `4` |

資料 `ARCHITECTURE.md` はPWM160の前後左右移動を実機で報告し、PWM120はトルク不足と記録する。ただし、各移動時の指令配列と実測の方向の対応、各輪の正負回転、旋回は記録から確定できない。現行コードの前進は全輪正、後退は全輪負という指令である。下表の横・旋回は運動学上の候補で、右左の確定ではない。`line_safety.h` の仮定では横成分は `(-w0+w1-w2+w3)/840`、前方は全輪和、旋回は左右群差で表す。床上の滑りや接続ミスはこの式では分からない。

| 選択 | PWM（`+`設定、配列0,1,2,3） | コード上の想定・確認状態 |
|---|---|---|
| `7` | +120,+120,+120,+120 | 前進指令。120で回るとは限らない |
| `8` | -120,-120,-120,-120 | 後退指令。同上 |
| `5` | -120,+120,-120,+120 | 横 A。資料上の右候補、実機左右未確定 |
| `6` | +120,-120,+120,-120 | 横 B。資料上の左候補、実機左右未確定 |
| `9` | -120,-120,+120,+120 | 旋回 A。右左未確定 |
| `0` | +120,+120,-120,-120 | 旋回 B。右左未確定 |

`-` は選んだ全パターンの符号を反転し、`+` は表の符号に戻す。MOTORの逆転保護は停止後200ms、指令が途切れた場合のwatchdogは100ms。実際の駆動時間や惰走は指令と異なる。

## 車輪を浮かせた試験

診断用MAINを別ビルドする例（作業ディレクトリは `rebuild2`、後述のコマンド自体はPC上でコンパイルするだけ）。出力先を競技用と分ける。

```powershell
arduino-cli compile --build-path "$env:TEMP/rcj-phase31-bench" --fqbn 'rp2040:rp2040:generic_rp2350:variantchip=RP2350B,flash=2097152_0,usbstack=picosdk' --libraries competition/libraries --build-property 'compiler.cpp.extra_flags=-DRCJ_SERIAL_TRIAL=0 -DRCJ_WHEELS_LIFTED_DIAGNOSTICS=1' competition/main
```

実際に書き込む場合は、既存MAINの復元方法と対象基板を確認してからユーザーが行う。診断版は競技用ではない。MOTOR・IR・OpenMVを変更する必要はない。MAINのUSBシリアルは115200、改行なしを選ぶ。停止中の `b` は青攻撃、`y` は黄攻撃としてログの攻撃／自陣表示を切り替える。開始時は `STATE=STOP`、`PWM_TRANSMITTED=0,0,0,0`、`IR_LINK=OK`、`CAMERA_LINK=OK`、`CAMERA_READY=1`、`LINE_HAZARD=0` を確認する。状態がおかしければ動力を切って原因を直す。

1. 1文字ずつ `s` → `M` → `1` → `+` → `g` → `R` と送る。`g` の後2秒以内に `R` を1回だけ送る。`1`ならM3のみ正値で短く回ることを、車輪の矢印を見て記録する。回らなければトルク不足・反転待ち・通信を疑い、正逆方向を推定しない。
2. 約150msで自動停止し再び手動停止になる。`R`連打では延長・再発火しない。試験ごとに `s` → `M` → 番号 → `+` または `-` → `g` → `R` を繰り返す。逆方向は停止から少なくとも200ms待ってから `R` を送る。
3. `1`〜`4`の各正負を確認し、その後 `7`,`8`,`5`,`6`,`9`,`0` を各1回ずつ試す。床から浮いているため、全輪の回転を観測できても機体が実際にどの向きへ動くかは判定できない。異音や意図しない車輪が動いたら直ちに外部動力を遮断する。
4. 異常中断を確認する試験も車輪を浮かせたまま行う。`s`、USB切断、IR通信断、カメラ通信断、白線危険のそれぞれで `PWM_TRANSMITTED` がゼロになり、自動で再駆動しないことを確認する。通信断ではMOTOR側の100ms watchdogも別途確認する。
5. 各回の `BENCH_PATTERN`（`0`選択は10と表示）、`BENCH_SIGN`、`BENCH_START_MS`、`BENCH_ELAPSED_MS`、`BENCH_LAST_PWM` と、MAINの `PWM_TRANSMITTED`、MOTORの `PWM_RECEIVED` / `PWM_APPLIED` / `REVERSE_WAIT` を保存する。通常ログは約1秒周期なので150msパルスの瞬間を捕捉できない。`BENCH_LAST_PWM` はMAINが最後に作った指令であり、実際のMOTOR出力・車輪の回転を証明しない。時刻と実出力はMOTOR側ログや計測器で別に確認する。

## IR強度と距離

モーター動力を切って機体と発光中のボールを固定。照明・電池・球の発光状態、IR基板の位置と向きを記録。機体中心またはIR受光面のどちらを原点としたか明記し、ボール中心まで巻尺で測る。前方0°で例として10/20/30/40/50/75/100cm、さらに左右45°・90°でも同様に測る。各点で固定後10秒以上のMAINログを保存し、`IR_LINK`, `IR_ANGLE`, `IR_STRENGTH`, `IR_AGE_MS` を記録。ボールなしも取る。必要ならIR基板のUSB 115200で `i` を送って `COUNTS` と `IR_STRENGTH` を記録する。各距離の最小・中央値・最大と欠測、角度ごとの重なりを表にする。値0は受光ゼロで、角度0が必ず正面に球ありを意味しない。複数距離で強度範囲が重なる場合、単一のしきい値による距離判定を採用しない。

## 白線の視野・死角と停止距離

1. 動力を切り、固定した機体の周囲に実際の白線と同じ幅の白テープを置く。前を0°として22.5°刻みで全周、特に左右90°・270°を確認。各角度で機体外縁から白線までの実距離を例として10/20/30/45/60cmに置き、白線の両端、ミラー、遮蔽物を撮影する。
2. MAINの `LINE_ANGLE`, `LINE_DISTANCE`, `LINE_HAZARD`, `SAFE_MASK`, `CAMERA_AGE_MS`, `FRAME_MS` とOpenMVの `OBSERVED_MASK`, `UNKNOWN_MASK`, `LINE_MASK`, `READY` を記録。OpenMVのUSB診断は `i`。角度0は前、16ビットのbit 0から時計回り22.5°刻み。見えない、反射、配線、部分遮蔽、線の切れ目、異なる照明を別々に試す。値が出ない方向は安全とは扱わない。機体外縁と画像上の距離は別物なので実測と比較する。
3. 停止距離は診断パルスや指令ログから推定できない。独立した動力遮断、十分な無障害の広さ、記録用カメラ／計測器、固定担当と操作者を準備し、別途承認された床上試験手段を用意してから、左右別・PWM別・電池状態別・床別に反復する。開始位置からの移動距離に加え、停止指令を出した瞬間から完全停止までの距離、応答遅延、最大値、機体外周の掃引範囲を動画等から測る。未確認の床上横移動をこの浮上専用診断版で実行しない。
4. センサーが線を検知した最遠・最近距離、全遅延中の移動と最大惰走、機体外周、死角、余裕を一緒に評価する。見通しと余裕を実測で証明できない方向は未校正のままにする。

## 回帰試験と履歴の復元

この `rebuild2` 自体は `.git` を持たず、試験は以前の `44cd80b` と `3636020` を `git show` で参照する。今回、公式リモートを一時ディレクトリへ読み取り専用cloneし、2コミットがあることを確認した。再実行時は履歴を保持したcloneの `.git` を一時的な `GIT_DIR` に設定し、SHA-256が `a300ff984b8852cb96624f5d29088f6336f0885bd7125e69d2df06b065412d9e` の元ZIPを `competition/scripts/test.py --zip <ZIP>` に指定する。ホストC++コンパイラーが必要。これは作業フォルダーをGitリポジトリに変換しない。

履歴復元後、Python試験は35/35成功。標準スクリプトは最初のC++失敗で停止するため、全テストを個別に同じ入力・判定で実行して調査した。失敗6件はPhase 3変更前バックアップでも同じ位置で再現した。`firmware` と `serial_trial` は `IR_NO_REPLY` と現行の `IR_INVALID` の期待不一致、`sweep` は現行 `decide` が試験対象のSweep設定を使用しない、`basic_chase` は既定の `RCJ_SERIAL_TRIAL=1` とビルド設定が競合、`managed_competition` と `start_wait` は古いモード・起動操作の期待が現行と一致しない。テストは削除・緩和していない。競技版の180件のPWMスナップショットはPhase 3前のバックアップと一致。診断のホスト試験、Phase 3シミュレーション試験、現行の起動・カメラ・ゴール・オウンゴール試験は成功した。
